# Inference stacks, memory and throughput for open ASR / speech-LLM models on cloud GPUs (Nov 2026)

Context: home PC is an RTX 3070 Ti 8 GB (Ampere, SM 8.6) with 60 GB RAM, x86. Planned work: an open-model
bake-off on a ~4 h gold set, then possibly a full run over ~6,500 h of English lecture audio.
Labels used below: **[vendor]** = figure from the model's publisher or a company selling the stack;
**[community]** = blog, forum or aggregator; **[est]** = my own arithmetic (params x bytes per weight),
not measured. The leaderboard paper measured all RTFx figures on one A100-SXM4-80GB at batch 64, using short
utterances. Long-form throughput on hour-long lectures will be different (see Gaps).

## Q1. Memory needs per model and precision (incl. KV-cache / long-audio growth), with a per-model table

### Takeaway
Only Nemotron-3.5-Transcribe (34B MoE), Qwen3-Omni (30B MoE), Voxtral Small (24B) and possibly Granite 8B / VibeVoice 9B / Kimi-Audio 7B need more than 24 GB at bf16. Every other candidate (Whisper, Parakeet, Canary, Cohere, Qwen3-ASR, Granite 2B, Voxtral Mini) fits its bf16 weights in under 10 GB, so batch size and KV cache decide how much VRAM you actually need. One 80 GB H100/A100 or one 96 GB RTX PRO 6000 Blackwell runs every model on the list at bf16 or fp8. Qwen3-Omni at bf16 is the tightest fit: the vendor's stated minimum is 79 GB for 15 s of video input via transformers.

#### Other memory facts
- Nemotron-3.5-Transcribe: "capacity planning should use the full 34B figure" (not the 4B active), because all experts must be resident ([search summary of guides](https://hackernoon.com/nvidia-nemotron-35-transcribe-a-complete-guide-to-the-speech-ai-model)) [community]; most of the 34B sits in experts that each token mostly skips ([openclawdc](https://openclawdc.com/blog/can-i-run-nemotron-3-5-transcribe-locally/)).
- Nemotron long-audio budget: the official recipe uses `--max-model-len 65536` and `max_tokens 16384`, and warns that long recordings need room for both audio input and transcript output. Audio caps are `VLLM_MAX_AUDIO_DECODE_DURATION_S=3600` and `VLLM_MAX_AUDIO_CLIP_FILESIZE_MB=180`. It also sets `--mamba-cache-mode none`, `--no-enable-prefix-caching` and `--mm-processor-cache-gb 0` ([NeMo docs](https://docs.nvidia.com/nemo/speech/nightly/speechlm2/nemotron_transcribe.html)).
- Qwen3-ASR: lower `max_inference_batch_size` to avoid OOM; examples set vLLM `gpu_memory_utilization` between 0.65 and 0.9 ([HF card](https://huggingface.co/Qwen/Qwen3-ASR-1.7B)).
- VibeVoice: Microsoft's template uses 80% of VRAM and does not account for the audio encoder's forward-pass peak ([HF discussion](https://hf-2025.pages.dev/microsoft/VibeVoice-ASR/discussions/21)) [community]. The usual OOM fix is to lower `--max-model-len` ([Baseten](https://docs.baseten.co/examples/models/transcription/vibevoice)).

### Inferences
- Rule of thumb for weights: bf16 ≈ 2 bytes/param, fp8/int8 ≈ 1, 4-bit ≈ 0.55–0.6. The Nemotron GGUF sizes fit this: F16 62.8 GiB for ~33B decoder params; Q8_0 32.6; IQ4 18.3. Add KV/state cache plus activations: a few GB for small batches, tens of GB for vLLM at high concurrency, since vLLM preallocates `gpu_memory_utilization` × VRAM anyway.
- Nemotron's hybrid Mamba backbone keeps per-token state smaller than a pure-attention 30B model's KV cache. This and the 1-hour single-pass design probably explain why one H100 can serve 1-hour inputs. The NeMo page doesn't say this explicitly.
- For hour-long lectures, three families **must be chunked**: Canary-Qwen (40 s training limit), Qwen3-ASR on vanilla vLLM (>10 min per request fails per Baseten), and the Whisper family (30 s windows, which faster-whisper/WhisperX handle with VAD). Three can take full talks in one pass: Nemotron (60 min), VibeVoice (60 min) and Voxtral (30 min transcription).
- Home RTX 3070 Ti 8 GB fits: Whisper (all), Parakeet, Canary-1B-v2, Cohere 2B, Qwen3-ASR 0.6B/1.7B, Granite 2B, and probably Voxtral Mini at small batch (9.5 GB stated, so borderline or needs int8). Nemotron, Qwen3-Omni, Voxtral Small, VibeVoice, Kimi-Audio and Granite 8B need cloud or CPU offload.

### Gaps
- No official VRAM numbers for Cohere Transcribe, Granite Speech, Canary-1B-v2, Parakeet, Step-Audio 2 or MiMo-Audio, and no audio-only memory figure for Qwen3-Omni (the published table measures video).
- The Nemotron FP8 checkpoint's exact footprint wasn't found. ~34–36 GB is inferred from the Q8_0 GGUF size.
- Kimi-Audio's 23 GB figure comes second-hand. I did not read the original model card.
- No source quantified KV-cache growth per minute of audio for any model.

## Q2. Which inference stacks support each model, and what throughput (RTFx) to expect

### Takeaway
vLLM (latest 0.33.0, released 2026-11-02) is now the common denominator. Its OpenAI `/v1/audio/transcriptions` table includes Whisper, Voxtral, Qwen3-ASR, Qwen3-Omni (thinker), Granite Speech, Canary-1B-v2, Cohere Transcribe, Nemotron-3.5-Transcribe and VibeVoice-ASR-HF. Parakeet-TDT runs through a plugin. Kimi-Audio is supported only as a generative audio-chat model, and Step-Audio 2 is supported only via vLLM-Omni. On throughput, Parakeet (~3,300 RTFx) and Canary-1B-Flash/v2 (750–1,050) are an order of magnitude faster than speech-LLMs: Canary-Qwen 418, Cohere 525 [vendor], Nemotron 270–410 on H100 [vendor], Qwen3-ASR-1.7B ~380 on vanilla vLLM, Whisper-v3 ~146, Voxtral Mini ~110.

- Qwen3-ASR-1.7B concurrency scaling, hardware unstated: RTF 0.01482 at c=1, 0.02072 at c=8, 0.07360 at c=64, 0.13056 at c=128; ~870 audio-s/s at c=64 ([emergentmind](https://api.emergentmind.com/topics/qwen3-asr-1-7b)) [aggregator]. This conflicts with Baseten's ~380x for vanilla vLLM at c=64 on RTX PRO 6000 ([Baseten](https://baseten.co/blog/fastest-lowest-cost-qwen3-asr-batch-transcription)) [vendor].
- Cohere reports RTFx 525 vs Whisper Large v3 146 and omniASR 7B-LLM 66 ([Cohere Arabic blog](https://huggingface.co/blog/CohereLabs/cohere-transcribe-arabic-07-2026-release)) [vendor]. No independent replication found.

### Inferences
- Full-archive compute time from these RTFx figures (6,500 h = 23.4M audio-seconds), single GPU, short-utterance batched figures, so treat as optimistic [est]: Parakeet-TDT ~3,333 RTFx ≈ **2 h** (A100); Canary-1B-v2 749 ≈ 8.7 h; Cohere 525 ≈ 12.4 h; Canary-Qwen 418 ≈ 15.6 h; Nemotron BF16 H100 270–410 ≈ **16–24 h** (open-source vLLM; NIM claims would be ~3 h on RTX PRO 6000); Qwen3-ASR-1.7B vanilla vLLM ~380 ≈ 17 h; Whisper-large-v3 146 ≈ 45 h; Voxtral Mini 110 ≈ 59 h. All of these fit in a few days on one GPU or under a day on 2–4.
- The 4 h gold set is minutes of compute for any model. Model download, kernel warmup and environment setup will dominate the bake-off, not inference.
- One vLLM install will not serve every model. Nemotron wants vLLM 0.32.0 plus the NeMo plugin and Python 3.13; Microsoft's VibeVoice image pins vLLM 0.14.1; Voxtral needs `mistral-common[audio]`; the Qwen3-Omni card suggests a fork. Plan for separate venvs or containers per family, which matches this repo's existing `asr/envs/*` pattern.

### Gaps
- No Open ASR RTFx found for Qwen3-ASR (the card's 147.93 has no hardware stated), Voxtral Small, Kimi-Audio, Step-Audio 2, MiMo-Audio, VibeVoice-ASR or Qwen3-Omni.
- No long-form (hour-long single file) RTFx was published for any model except Baseten's Qwen3-ASR claim. The leaderboard paper gives no long-form RTFx.
- TensorRT-LLM support for these speech-LLMs was not confirmed. The Nemotron card does not mention it. Only Whisper has a long-known TRT-LLM example, and I didn't verify that here.
- Whisper-large-v3-turbo RTFx sources conflict (216 vs 794), and neither states its GPU.

## Q3. FP8 / NVFP4 / int support by GPU generation (Ampere vs Ada vs Hopper vs Blackwell)

### Takeaway
Native FP8 compute needs SM 8.9+ (Ada L4/L40S/RTX 40, Hopper H100/H200, Blackwell). Native NVFP4 needs Blackwell (B200/GB200, RTX PRO 6000, RTX 50, DGX Spark). On Ampere (A100, A10, RTX 30, including the home 3070 Ti) vLLM runs FP8 and NVFP4 checkpoints only as **weight-only** (W8A16 / W4A16) via Marlin kernels. That saves memory but not compute, and can be slower than bf16 at large batch. NVIDIA's Nemotron card lists FP8 for H100/H200/L40S/Blackwell and NVFP4 for Blackwell only, while BF16 runs on A100 80GB too.

### Cited Findings
- vLLM: FP8 compute requires compute capability ≥8.9 (Ada, Hopper, Blackwell). Capability ≥7.5 (Turing, Ampere) gets weight-only W8A16 via FP8 Marlin ([vLLM FP8 docs](https://docs.vllm.ai/en/latest/features/quantization/llm_compressor/fp8/)).
- On Ada (SM 8.9), **block-wise** FP8 checkpoints fail the CUTLASS check (no TMA/wgmma) and fall back to Marlin. Marlin computes at 16-bit, so it can be slower than bf16 at large batch ([levelup write-up](https://levelup.gitconnected.com/blockwise-fp8-on-ada-gpus-why-your-l4-falls-back-to-marlin-measured-e74a0dfa3024)) [community].
- vLLM ModelOpt: without a native FP4 GEMM kernel, NVFP4 falls back to weight-only W4A16 via Marlin with a warning ([vLLM ModelOpt docs](https://docs.vllm.ai/en/latest/features/quantization/modelopt/)). Marlin FP4 dequantizes to BF16 and works on all Blackwell variants including SM121/DGX Spark ([NVIDIA forum](https://forums.developer.nvidia.com/t/psa-state-of-fp4-nvfp4-support-for-dgx-spark-in-vllm/353069?page=9)) [community]. vLLM 0.10.2 gated Marlin FP4 on capability 80, i.e. Ampere+ ([vLLM API docs](https://docs.vllm.ai/en/v0.10.2/api/vllm/model_executor/layers/quantization/utils/marlin_utils_fp4.html)).
- NVFP4 is a 4-bit format introduced with Blackwell ([edge-ai-vision](https://www.edge-ai-vision.com/2025/10/nvidia-blackwell-the-impact-of-nvfp4-for-llm-inference/)).
- Nemotron-3.5-Transcribe support matrix: microarchitectures Ampere, Blackwell, Hopper, Lovelace. BF16 on A100 80GB, B200, DGX Spark, GB200, GB300, Jetson Thor, RTX PRO 6000, H100, H200. **FP8** on B200, DGX Spark, GB200, GB300, Jetson Thor, RTX PRO 6000, H100, H200, **L40S** (the only Lovelace entry). **NVFP4: Blackwell only**, incl. RTX 5090 (NVFP4 only), RTX PRO 6000, DGX Spark ([HF card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Transcribe-30B-A4B)). The AD-NVFP4 GGUF is for Blackwell cards ([openclawdc](https://openclawdc.com/blog/can-i-run-nemotron-3-5-transcribe-locally/)).
- Canary-Qwen-2.5B lists support for Ampere, Blackwell, Hopper, Lovelace, Pascal, Turing, Volta, Jetson ([HF card](https://huggingface.co/nvidia/canary-qwen-2.5b)).
- CTranslate2 int8 / int8_float16 runs fine on the RTX 3070 Ti (Ampere): 2926 MB, 59 s for 13 min of large-v2 ([faster-whisper README](https://github.com/SYSTRAN/faster-whisper)).

### Inferences
- For a cloud bake-off, the GPU choice is: **H100/H200 80–141 GB** (FP8 native, the reference platform for Nemotron's published numbers), **RTX PRO 6000 Blackwell 96 GB** (FP8 + NVFP4 native, the platform for Baseten's and NIM's top numbers), **L40S 48 GB** (FP8 native, cheaper; Nemotron FP8 is listed, BF16 isn't), or **A100 80 GB** (BF16 only; matches the Open ASR Leaderboard's RTFx hardware, so its numbers compare directly).
- GGUF k-quants/IQ quants (llama.cpp / NeMo-Speech.cpp) work on any CUDA generation, including Ampere. So on non-Blackwell hardware, a Q4/Q5 GGUF is the practical low-memory Nemotron route.

### Gaps
- No authoritative table found for which vLLM NVFP4 kernel is selected on SM 8.9 specifically. The official vLLM "supported hardware" quantization page returned 404 at its old URL.
- No measured accuracy comparison of Nemotron BF16 vs FP8 vs NVFP4 on English beyond the community note that the Q2 GGUF stays within noise for English ([openclawdc](https://openclawdc.com/blog/can-i-run-nemotron-3-5-transcribe-locally/)).

## Q4. CPU-offload options (MoE expert offload, accelerate device_map) and when a big-RAM CPU server is viable

### Takeaway
Little hard data exists. The only Nemotron-specific guidance is "move some experts to system RAM" for GPUs under 16 GB, with no method or speeds given. For the MoE models (Nemotron 4.3B active, Qwen3-Omni 3B active), GGUF with experts in system RAM is the plausible way to run them on the home 3070 Ti + 60 GB RAM for small tests. A pure CPU server is only realistic for the small models (Parakeet, Whisper int8, Canary) via ggml/CTranslate2, not for a 6,500 h run with a speech-LLM.

### Cited Findings
- Nemotron on 12 GB: AD-Q2_0_M is too big for the GPU alone; the guide says to "move some experts to system RAM" but gives no method or figures ([openclawdc](https://openclawdc.com/blog/can-i-run-nemotron-3-5-transcribe-locally/)) [community].
- NeMo-Speech.cpp has a CPU backend alongside CUDA/Metal/Vulkan ([openclawdc](https://openclawdc.com/blog/can-i-run-nemotron-3-5-transcribe-locally/)). Parakeet runs on CPU via parakeet.cpp in LocalAI ([LocalAI blog](https://localai.io/blog/parakeet-cpp-asr-on-cpu/)).
- A third-party press item reports that AtomicChat made Nemotron 3.5 Transcribe run on consumer GPUs via quantized GGUFs ([hermes-ai](https://hermes-ai.net/news/atomicchat-makes-nvidia-s-nemotron-3-5-transcribe-run-on-consumer-gpus/)) [community].
- Kimi-Audio at 4-bit: ~8 GB, "slower" ([Replicate](https://replicate.com/zsxkib/kimi-audio-7b-instruct)) [community].
- Arm's DGX Spark material runs faster-whisper on the Arm **CPU**, not CUDA ([Arm learning path](https://learn.arm.com/learning-paths/laptops-and-desktops/dgx_spark_voicechatbot/4_vllm/)).

### Inferences
- From general knowledge, not verified in this session: llama.cpp-family runtimes put MoE expert tensors on CPU via `--override-tensor`/`-ot` or `--n-cpu-moe`. vLLM has `--cpu-offload-gb`, and transformers/accelerate has `device_map="auto"` with `max_memory`. Whether NeMo-Speech.cpp inherits llama.cpp's `-ot`/`--n-cpu-moe` flags was not confirmed.
- Home PC estimate [est]: Nemotron AD-IQ4_NL (19.9 GiB) with ~6 GB on the 3070 Ti and the rest of the experts in 60 GB RAM should load. Speed is unmeasured, and 4.3B active params per token over DDR4 likely means a few tokens per ms at best. It is fine for spot checks of a few clips, not for the gold set at scale.
- A big-RAM CPU-only server only makes sense for Parakeet/Whisper-int8 class models. For speech-LLMs it would be orders of magnitude slower than one rented GPU-hour.

### Gaps
- No measured throughput for any expert-offload configuration of Nemotron or Qwen3-Omni.
- No measured CPU-only RTFx for Parakeet/Canary/Whisper on server CPUs was gathered in this session.

## Q5. ARM64 (GH200 / Grace) compatibility

### Takeaway
As of Nov 2026, PyTorch (2.11+), vLLM (0.33.0) and SGLang (0.5.23) all ship aarch64 manylinux wheels on PyPI, so GH200 is viable for the vLLM-served models. **CTranslate2 4.9.0's aarch64 wheel is CPU-only**: I checked the binary and it reports "not compiled with CUDA support". faster-whisper/WhisperX on a GH200 GPU therefore needs a source build of CTranslate2 or an NGC base image. NeMo is pure-Python (`py3-none-any`) but pulls compiled deps. I did not verify its aarch64 dependency chain.

### Cited Findings
- Starting with PyTorch 2.11.0, the default `pip install torch` on aarch64 Linux pulls a CUDA-enabled wheel (previously CPU-only by default) ([PyTorch blog](https://pytorch.org/blog/vllm-and-pytorch-work-together-to-improve-the-developer-experience-on-aarch64/)). torch 2.15.0 ships `manylinux_2_28_aarch64` wheels for cp311–cp315 ([PyPI torch](https://pypi.org/project/torch/)).
- vLLM 0.33.0 ships `vllm-0.33.0-cp38-abi3-manylinux_2_28_aarch64.whl` alongside x86_64 ([PyPI vllm](https://pypi.org/project/vllm/)). In Aug 2025 (vLLM 0.10.1-gptoss) there was no aarch64 wheel ([vLLM forum](https://discuss.vllm.ai/t/unable-to-use-vllm-0-10-1-gptoss-on-gh200-aarch64-source-for-custom-wheel-not-available/1320)), so this gap is now closed for mainline vLLM. Plugin/fork pins (VibeVoice's vLLM 0.14.1, Qwen3-Omni's fork) may predate aarch64 wheels.
- SGLang 0.5.23 ships `manylinux_2_34_aarch64` wheels ([PyPI sglang](https://pypi.org/project/sglang/)).
- CTranslate2 4.9.0: aarch64 manylinux wheels exist (19.1 MB vs 42.8 MB for x86_64). Inspecting `libctranslate2…so.4.9.0` from the cp312 aarch64 wheel shows no cuBLAS/cuDNN references, and the string "This CTranslate2 package was not compiled with CUDA support" (own check of [PyPI ctranslate2 4.9.0](https://pypi.org/project/ctranslate2/4.9.0/#files), 2026-11-10). The speaches project reports the same: no CUDA ctranslate2 wheel for linux/arm64, silent CPU fallback, fix by building from source on an NGC base image ([speaches #620](https://github.com/speaches-ai/speaches/issues/620)).
- nemo-toolkit 3.0.0 is a `py3-none-any` wheel ([PyPI nemo-toolkit](https://pypi.org/project/nemo-toolkit/)).
- An NVIDIA forum thread reports LLM-engine issues on Arm64 + GH200 ([NVIDIA forum](https://forums.developer.nvidia.com/t/arm64-gh200-llm-engine-issues/339136)) [community; details not read].
- Nemotron's card lists ARM platforms (DGX Spark GB10, GB200/GB300, Jetson Thor) among supported hardware, without saying "aarch64" explicitly ([HF card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Transcribe-30B-A4B)).

### Inferences
- GH200 (96 GB HBM3 + ~480 GB LPDDR via NVLink-C2C) suits the vLLM-served speech-LLMs (Nemotron BF16, Qwen3-Omni). It is a poor fit for the faster-whisper baseline and for anything that needs custom CUDA extensions without aarch64 wheels (e.g. flash-attn builds, some NeMo deps like Mamba/causal-conv kernels). An x86 H100 avoids all of these.
- The repo's `asr/common.py` preloads CUDA libs from `nvidia-*-cu12` wheels, which is x86-oriented. On aarch64 those wheels may differ, which needs a check if a GH200 is chosen.

### Gaps
- NeMo-toolkit's compiled dependencies on aarch64 (e.g. `mamba-ssm`, `causal-conv1d`, `nemo_text_processing`/pynini) were not verified.
- Whether Microsoft's VibeVoice Docker image and the `qwenllm/qwen3-asr` image publish arm64 variants was not checked.

## Q6. Practical gotchas (CUDA versions, drivers, Docker images)

### Takeaway
The main friction points are version pins that conflict across model families, and default audio-length caps in vLLM. Nemotron needs vLLM 0.32.0 + NeMo `main` + Python 3.13 + av 19.0.2 (which clashes with this repo's `av<19` pin for faster-whisper). VibeVoice needs Microsoft's vLLM 0.14.1 image. Qwen3-ASR wants Python 3.12 + cu129 vLLM nightlies. NeMo-Speech.cpp needs CUDA 12.8+ for batched CUDA. Use one container or venv per family.

### Cited Findings
- Nemotron: `av==19.0.2` required ([NeMo docs](https://docs.nvidia.com/nemo/speech/nightly/speechlm2/nemotron_transcribe.html)). This repo caps `av` <19 for faster-whisper 1.2.1 (project CLAUDE.md), so the two cannot share an env.
- Nemotron vLLM: default max audio decode is 600 s; set `VLLM_MAX_AUDIO_DECODE_DURATION_S=3600` and `VLLM_MAX_AUDIO_CLIP_FILESIZE_MB=180` for 1-h files ([HF card](https://huggingface.co/nvidia/NVIDIA-Nemotron-3.5-Transcribe-30B-A4B), [NeMo docs](https://docs.nvidia.com/nemo/speech/nightly/speechlm2/nemotron_transcribe.html)).
- NeMo-Speech.cpp: CUDA 12.8+ for the batched CUDA path. Keep the encoder GGUF filename unchanged, because the decoder file references it by name ([openclawdc](https://openclawdc.com/blog/can-i-run-nemotron-3-5-transcribe-locally/)). NGC container available ([NGC](https://catalog.ngc.nvidia.com/orgs/nvidia/-/containers/nemo-speech.cpp/-)).
- Qwen3-ASR: Python 3.12 recommended; vLLM nightly via cu129 wheels; Docker `qwenllm/qwen3-asr:latest` with `--gpus all --shm-size=4gb`, bind to 0.0.0.0, NVIDIA Container Toolkit required. Optional FlashAttention 2 build: use `MAX_JOBS=4` if RAM < 96 GB ([HF card](https://huggingface.co/Qwen/Qwen3-ASR-1.7B)).
- Qwen3-Omni: transformers must be installed from source; the card's vLLM example uses a fork with `VLLM_USE_V1=0` ([HF card](https://huggingface.co/Qwen/Qwen3-Omni-30B-A3B-Instruct)). Mainline vLLM now lists the thinker ([vLLM](https://docs.vllm.ai/en/latest/models/supported_models.html)), so the card is likely stale.
- VibeVoice: plain `vllm serve microsoft/VibeVoice-ASR` failed; use Microsoft's Docker plugin pinned to vLLM 0.14.1 ([vLLM issue #39964](https://github.com/vllm-project/vllm/issues/39964)). Alternatively use the `-HF` checkpoint through the vLLM Transformers backend ([vLLM](https://docs.vllm.ai/en/latest/models/supported_models.html)).
- Voxtral: vLLM ≥0.10.0, `mistral_common ≥1.8.1`, mistral tokenizer/config/load flags ([HF card](https://huggingface.co/mistralai/Voxtral-Mini-3B-2507)).
- Canary-Qwen: "latest trunk version of NeMo, and PyTorch 2.6+" ([HF card](https://huggingface.co/nvidia/canary-qwen-2.5b)).
- Open ASR Leaderboard reference environment: driver 560.28.03, CUDA 12.6 ([Open ASR paper](https://arxiv.org/html/2510.06961v3)).
- faster-whisper benchmarks were run with CUDA 12.4 on an RTX 3070 Ti 8 GB ([faster-whisper README](https://github.com/SYSTRAN/faster-whisper)).

### Inferences
- Pick a cloud image with a recent driver (R570+ supports CUDA 12.8/12.9 and the cu129 wheels; Blackwell needs CUDA 12.8+ anyway). Avoid hosts pinned to CUDA 12.4-era drivers. This is general knowledge, not sourced in this session.
- Suggested bake-off layout: (a) the existing `asr/envs/nemo` for Parakeet/Canary/Canary-Qwen; (b) a new vLLM-0.32 + NeMo-main + Py3.13 env for Nemotron; (c) a stock latest-vLLM env for Qwen3-ASR, Voxtral, Granite, Cohere, Canary-1B-v2 and Qwen3-Omni via `/v1/audio/transcriptions`; (d) Microsoft's Docker image for VibeVoice; (e) the main env for faster-whisper.

### Gaps
- Exact NGC NeMo container tags for NeMo 3.0 / Nemotron Transcribe, and whether an official vLLM Docker image bundles the NeMo Speech plugin, were not found.
- Minimum driver versions per stack were not explicitly sourced.
